# 仓库结构与时序

本文件回答两件事：**东西放在哪**，以及**一次改动是怎么从开发机走到目标机、再沉淀回文档的**。

## 1. 一次改动的完整路径

```text
   开发机（Windows）                 构建宿主（x86_64 Debian 交叉编译）            目标机（GK-W76 平板）
 ┌──────────────────┐              ┌────────────────────────────────┐        ┌──────────────────────────┐
 │ source of truth  │   git push   │ 1) 解包 stable 源码（不带 .git）│        │ 5) scripts/gk-install-   │
 │ scripts/ tools/  │ ───────────► │ 2) 逐个应用补丁（社区集+本项目）│        │    kernel.sh 新增 BLS 条目│
 │ patches/ docs/   │              │ 3) 构建 Image / DTB / modules  │        │ 6) 重启进新条目，实测复核 │
 └──────────────────┘              │ 4) 门禁断言 → 打包 → 发 Release │        └──────────────────────────┘
          ▲                         └────────────────────────────────┘                    │
          │                                        │                                      │
          │                                        ▼                                      ▼
          │                         ┌──────────────────────────────┐        ┌──────────────────────────┐
          └─────────────────────────│ GitHub Release（8 项资产）    │◄───────│ dmesg / /proc/interrupts │
              结论与数字回写 docs/   │ + docs/releases/<tag>.md     │        │ bench 工具 / sysfs 观测节点│
                                    └──────────────────────────────┘        └──────────────────────────┘
```

要点：

- **构建永远在构建宿主上做**，目标机只负责安装与实测（平板无风扇，编译会触发硬件级断电）。
- **产物经 GitHub Release 分发**，目标机只从 Release 资产安装，不从开发机直接拷。
- **实测数据回写 `docs/`**：发布说明、基准数据、结论与教训都落在文档里，而不是留在聊天记录里。

## 2. 目录职责

| 目录 | 面向谁 | 职责 | 是否改系统 |
|---|---|---|---|
| [`scripts/`](../scripts/README.md) | 目标机用户 | 设备鉴别、装机、触屏/音频修复、诊断报告、内核安装 | 是（多数支持 `DRY_RUN`） |
| [`tools/`](../tools/README.md) | 开发机 / 构建宿主 / 目标机 | 只读分析工具 + 构建与打包脚本 | 否 |
| [`patches/`](../patches/README.md) | 内核树 | 分序列的补丁、应用顺序（`series`）与元数据 | 否 |
| [`config/`](../config/) | 目标机 | 运行期配置（如 gaokun3 专用 ALSA UCM2 profile） | 是（由脚本安装） |
| [`docs/`](README.md) | 所有人 | 实机结论、决策记录（`adr/`）、提案（`rfc/`）、发布说明（`releases/`） | 否 |
| `.github/` | 贡献者 | CI、issue/PR 模板、CODEOWNERS、依赖更新 | 否 |

## 3. 三条原则

1. **单一事实来源**：结论、数字与判据只写在 `docs/`（发布说明在 `docs/releases/`）。
   脚本与工具只负责产出数字；README 只做导航与状态摘要。
2. **脚本可复现**：能自动化的检查就不要靠人记 —— `make check` 与 CI 是同一组规则
   （见 [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) 与 [`Makefile`](../Makefile)）。
3. **补丁可上游**：本地修复优先做成能提交上游 Linux 的补丁，放进 `patches/` 并标注上游状态；
   永久停留在仓库内的分叉要有 ADR 说明理由。

## 4. 状态与置信度

- 文档里的每条结论都标注置信度：`【已核实】`（实机或一手源码）、`【社区报告】`、`【推测】`。
- 文档状态分四级：`已实机核实` / `部分核实` / `历史归档` / `规划中`，索引见 [`docs/README.md`](README.md)。
- **结论被推翻时不要删旧文**：保留原文并加显式更正块，说明何时、被什么证据推翻
  （例：[`docs/touch-idle-policy.md`](touch-idle-policy.md) 与 [`docs/video-decode.md`](video-decode.md) 开头的更正块）。
