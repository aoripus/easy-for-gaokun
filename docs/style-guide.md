# 文档写作规范

> 适用范围：本仓库 `docs/`、`README.md`、`CHANGELOG.md`、`CONTRIBUTING.md` 以及各类模板中的**正文文字**。
> 目标只有一个：**让下一个拿着同一台机器的人能复现你的结论，或者明确知道复现不了**。

本仓库的文档不是研究笔记，而是实机结论的沉淀。因此本规范的重点不是"文笔"，
而是**可复现性**与**置信度**：一句话如果无法被验证，就必须标明它只是推测。

---

## 1. 语言

| 规则 | 说明 |
|---|---|
| 正文用**简体中文** | 包括标题、表格表头、图注、提交信息正文（见 [`../CONTRIBUTING.md`](../CONTRIBUTING.md)） |
| 命令、路径、标识符**保留英文原文** | `uname -r`、`/dev/input/event11`、`CONFIG_VIDEO_QCOM_VENUS`、`himax_lock()`、`gaokun3` 一律不翻译、不改写大小写 |
| 中英文之间加**空格** | ✅ `内核串`7.2.5-aoripus-ml-gaokun3-eog-el1-venus-r3` 无尾部 `+`` · ❌ `内核串7.2.5...无尾部+` |
| 数字与单位之间加**空格** | ✅ `120 Hz`、`30 ms`、`24,734,208 B`、`0.50%` · ❌ `120Hz`、`30ms` |
| 中文标点用全角，英文/代码内用半角 | 括号、引号、顿号按此区分；代码块内一律半角 |
| 不用第一人称口语 | ✅ "实测得到" · ❌ "我试了一下发现" |

反例（同一个意思，两种写法）：

```text
❌ 我们把idle_enter_frames改成了7200帧,大约60秒
✅ 把 `idle_enter_frames` 改为 7200 帧（≈60 s）
```

## 2. 结论必须标注置信度

全仓库统一三个标识，**放在结论所在的那句话或那一行里**（表格则单独成列），不要只在文首声明一次：

| 标识 | 含义 | 什么时候可以用 |
|---|---|---|
| **【已核实】** | 本机实测，或直读一手源码 / 固件 / 官方 API / 原作者邮件 | 必须能给出可复现的命令或可指认的源码位置 |
| **【社区报告】** | 论坛、邮件列表、他人仓库或第三方实测 | 必须能给出链接或出处 |
| **【推测】** | 本项目推断，尚未验证 | 必须写清推断依据与**如何验证** |

写法示例：

```text
- 空闲时 `gpio175` 电平占空比为高 99.1%（2 s / 1882 次采样）⇒ INT 是干净脉冲。【已核实】
- 上游 venus 的 `core.h` 里有 `#if (!IS_ENABLED(CONFIG_VIDEO_QCOM_IRIS))` 守卫，
  一旦启用 iris，venus 的 IRIS2 / HFI-6XX 支持会被整体编译掉。【已核实】
- 本机 TZ 固件可能把视频子系统状态机实现在 QTEE 侧。【推测】（依据：Windows 侧调用序列；验证方式：见 §7）
```

**口径必须与 [`README.md`](README.md) 一致**。若某条结论的证据等级发生升降，改标识的同时要写清"为什么升降"。

## 3. 可复现性

### 3.1 给命令，而不是给结论

不要写"已确认 SPI 走 GSI 模式"，要写清**如何看出来**：

```bash
# 空闲 20 s 窗口、两次采样取增量
grep -E 'gpi-dma|998000.spi|msmgpio' /proc/interrupts
```

### 3.2 贴输出必须注明取得条件

任何实测输出都要说明**在哪台机器、哪个内核串、什么条件下**得到：

```text
$ uname -r
7.2.5-aoripus-ml-gaokun3-eog-el1-venus-r3
$ dmesg | grep 'started at EL'
[    0.008204] CPU: All CPU(s) started at EL1
```

> 取自已发布的 release notes（`docs/releases/`），机器为 GK-W76，面板点亮、无人触摸。

**禁止**只贴一行结论性数字而不给采集条件 —— 同一台机器在不同内核串上可以差 4 倍以上
（参见 [`bench/touch-bench-20260913.md`](bench/touch-bench-20260913.md) §4 里两处方向相反的偏差）。

### 3.3 禁止"已测试通过"式证据

| 不合格 | 合格 |
|---|---|
| "修复后已测试通过" | "修复后 `msmgpio 175` 中断计数由 1 涨到 90,419" |
| "性能有明显提升" | "每帧 IRQ 15.39 → 3.558，CPU 忙 14.97% → 5.56%" |
| "官方 ISO 不可用" | "官方 Ubuntu ISO 无法在这台机器上启动（原因见 `docs/25`，本仓库未收录）" |

引不出具体观测量的结论，只能标 **【推测】**，并写清怎么才能验证它。

### 3.4 结论被推翻时**不要删除原结论**

本仓库允许并鼓励"留痕式更正"，做法是**在文档开头加一个更正块**，指明：

1. 原文写的是什么、为什么现在不成立；
2. 新的结论是什么、依据是什么；
3. 原文哪一部分仍然有效（例如"逐寄存器验证部分仍然完全有效"）。

被推翻的原文保留在下方，**不改写历史**。范例见 [`video-decode.md`](video-decode.md) 开头的更正块。

### 3.5 测量工具本身也要被质疑

若结论建立在"操作 A 之后现象 B 消失"上，必须先证明 **A 只做了它声称的事**。
本仓库有过真实事故：`himax_lock()` 屏蔽中断而 `himax_unlock()` 从不恢复，
导致"写 sysfs"这个动作本身改变了被测对象，连续污染两轮实验
（见 [`touch-idle-policy.md`](touch-idle-policy.md) §3）。凡这类"因果归因"，必须在文中说明**排除干扰项的方法**。

## 4. 结构与排版

- **表格优先于长段落**：并列的事实、对照关系、状态清单一律用表格；段落只用来讲因果与结论。
- **一文一主题**：文档标题下第一段就要说清"这篇解决什么问题、适用范围是什么"。
- **小节编号**：长文用 `## 0.` 起编（结论速览放 `§0`），便于其它文档以"见 §7.11"精确引用。
- **代码块标注语言**：`bash` / `sh` / `dts` / `c` / `text` / `json` / `ini` / `js`。
  纯输出用 `text`，避免被当成可执行命令。
- **引用其它文档一律用相对路径**（见 §5）。
- **不放图片链接，除非文件已入库**：指向外部或未入库的截图会让文档在离线时不可读；
  需要展示界面时改用文字描述 + 关键输出。
- **禁止写入**：任何凭据、密钥、口令、个人邮箱、内网 IP。设备专有驱动与固件也**不得**入库
  （见 [`../CONTRIBUTING.md`](../CONTRIBUTING.md) §安全约束）。
- **不编造**：版本号、提交哈希、实测数字、上游结论，一律以实际读到的为准；
  查不到就写 `待核实`，不要"补一个看起来合理的"。

## 5. 交叉引用

- 仓库内引用**只用相对路径**，让 GitHub 与本地编辑器都能直接跳转：

```markdown
见 [`docs/kernel-7.2.5-el1-build.md`](kernel-7.2.5-el1-build.md)          <!-- 同目录 -->
见 [`patches/touch-idle/`](../patches/touch-idle/README.md)                <!-- 上一级 -->
见 [`bench/touch-bench-20260913.md`](bench/touch-bench-20260913.md)        <!-- 子目录 -->
```

- 引用**上游或外部**内容时用绝对 URL，并在同段落注明这是外部资料（如「【社区报告】」）。
- 引用**本机实测记录**时优先引用仓库内的文档，而不是复述数字 —— 副本会漂移。
- 每新增一篇文档，必须同时在 [`README.md`](README.md) 的索引表里登记（禁止孤儿文档）。

## 6. 文件与命名

| 对象 | 规则 | 示例 |
|---|---|---|
| 文档文件名 | 小写、**短横线分隔**、与内容对应 | `install-dualboot.md`、`touch-idle-policy.md`、`kernel-7.2.5-el1-build.md` |
| 带日期的实测记录 | 主题 + `-YYYYMMDD` | `bench/touch-bench-20260913.md` |
| 发布说明 | `docs/releases/<release-tag>.md`，**与 tag 同名** | `releases/kernel-7.2.5-aoripus-ml-gaokun3-eog-el1-venus-r3-20260913.md` |
| 内核串与 tag | 见 [`kernel-7.2.5-el1-build.md`](kernel-7.2.5-el1-build.md) §0.1 | `7.2.5-aoripus-ml-gaokun3-eog-el1-venus-r3` |
| 目录名 | 小写、短横线或语义化复数 | `releases/`、`bench/` |

同一主题的"决策"与"提案"分别放 `docs/adr/` 与 `docs/rfc/`（`docs/README.md` §3 登记其状态）。

## 7. 提交前自检

逐条勾选，缺一项就先别提交：

- [ ] 文首说明了**适用设备与适用范围**（GK-W76 / SC8280XP / `gaokun3`，或明确写"不适用于其它变体"）。
- [ ] 每个结论都带 **【已核实】/【社区报告】/【推测】**，且与 [`README.md`](README.md) 的口径一致。
- [ ] 实测数字都给了**命令 + 条件（机器 / 内核串 / 环境）**，没有孤立的"已测试通过"。
- [ ] 并列信息用了表格；长因果用段落；`§` 编号可被精确引用。
- [ ] 全部内部链接是**相对路径**，且目标文件真实存在。
- [ ] 新文档已在 [`README.md`](README.md) 索引表中登记。
- [ ] 无凭据 / 邮箱 / 内网 IP；无未入库的图片与专有文件。
- [ ] 无编造的版本号、提交哈希与实测数字；不确定处写 `待核实`。
- [ ] **编码 UTF-8（无 BOM）、行尾 LF、文件末尾有换行**（见下节）。

## 8. 编码与行尾

- **UTF-8，不带 BOM**（带 BOM 会让部分工具把文件首字符读成乱码）。
- **LF 行尾**。开发机通常是 Windows 而目标机是 Linux/aarch64，CRLF 会让 shell 脚本在目标机上无法直接执行，
  也会污染 DTS 与补丁；仓库用 `.gitattributes` 强制 LF。
- **文件末尾必须有一个换行**（POSIX 文本文件约定）。

提交前自检：

```bash
git config core.autocrlf false
grep -rlU $'\r' scripts docs patches   # 应无输出
```
